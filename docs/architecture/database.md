# Database design

## Foundation

PostgreSQL 17, synchronous psycopg 3 and SQLAlchemy 2.0. `Base.metadata` defines stable constraint naming. Alembic gets the same metadata and runtime URL through validated environment configuration. Baseline revision `0001_foundation` establishes version history only: there is no justified persistent business entity in the foundation. Alembic owns `alembic_version`; no health table or fake invoice tables are created.

Migrations are explicit commands, never startup side effects or `metadata.create_all()`. Review every generated revision, run it against a clean database/schema, test downgrade/reapply and run `alembic check` to detect model drift. Invoice models are registered in Alembic metadata.

Application engine resources belong to app lifespan. One session per request, closed in a dependency; use cases own transaction commits. Connection pre-ping and timeouts bound readiness failures. Close sessions to roll back uncommitted writes. Integration tests use a real explicitly configured `_test` database and random per-test schemas. Cleanup drops only each fixture's own schema, never a development database.

## Implemented in Task 02

- `invoices`: public invoice ID primary key (bounded 64), fictional vendor name, nullable issue date, due date, currency, checked status code, gross amount NUMERIC(18,2). Nullable VAT rate/net/VAT represent summary-only dashboard rows without fabricated extraction data. Complete canonical records must have consistent totals and positive line quantities.
- `invoice_items`: invoice FK, positive ordered position with unique `(invoice_id, position)`, description, quantity integer, unit net NUMERIC(18,2). Stored line net, if used, must match the deterministic calculator; avoid maintaining redundant values without a constraint/use case.
- `invoice_po_snapshots`: at most one matched PO snapshot per invoice, invoice FK unique/primary key, PO reference, nullable delivery receipt reference, explicit currency/VAT rate. This is an invoice-specific comparison snapshot, not a speculative reusable purchasing subsystem.
- `invoice_po_items`: snapshot FK plus matching invoice line position, quantity and PO unit net NUMERIC(18,2). Enforce matching relationships and reject inconsistent currencies. Task 02 validates matching quantities for the canonical demo; general reconciliation is later work.

Vendor remains a display string until a vendor-management use case exists. Do not introduce tenant/user/master-data tables before real identity and tenancy requirements. For the four visible summaries use only actually known fields; canonical INV-2026-1042 has three items and PO-2026-0871 / DR-2026-1042. Derived totals/comparison should be calculated by one independently tested financial module, not duplicated in repository and router.

Currency is explicit ISO code, money uses Decimal with two-place NUMERIC storage. Reject negative prices, nonpositive quantity and unsupported precision rather than silently truncating. ROUND_HALF_UP: line net first, sum for invoice net, then VAT on net and gross as net + VAT. UTC-aware timestamps use TIMESTAMPTZ when events are introduced; issue/due use DATE. Index due/status only when corresponding query patterns justify them. Sorting always has a stable ID tie-breaker.

## Development data and safety

Compose's `postgres-data` volume persists development data. `docker compose down` preserves it. The `postgres-test` profile has a separate ephemeral tmpfs database on port 5433. CI uses its own disposable PostgreSQL service. Never point integration tests at production/development databases or silently substitute SQLite.

The seed is explicit and uses one transaction with PostgreSQL conflict-safe inserts keyed by stable IDs. Existing invoices and their children are preserved. It requires `INVOICEFLOW_ENV=local` and a loopback database host (`localhost`, `127.0.0.1`, or `::1`); all other environments and hosts are rejected. Migrate the intended local database first, then run from `apps/backend`:

```powershell
$env:INVOICEFLOW_ENV = 'local'
uv run python -m invoiceflow.modules.invoices.seed
```

There is no startup or production seeding. See [local development](local-development.md) for safe database lifecycle commands.

## Reconciliation results

`invoice_reconciliations` stores the algorithm version, canonical input snapshot, SHA-256 input hash and calculated evidence in JSON, with an invoice foreign key, positive revision and a unique invoice/hash pair. Revisions are allocated while holding the invoice row lock. The processing-to-completed transition is atomic; failures leave no result. Future writers must acquire that same lock before changing invoice or PO inputs. Historical results remain available after inputs change.

## Planned compatibility extensions (05a and 07; no migration implemented)

Task 05a adds a read service over completed `invoice_reconciliations`, retaining the existing rows and JSON payloads. It uses the Task 04 canonical input hash routine to compare a stored revision with current inputs without writing. An invalid or missing current input yields `is_current=false`; it does not hide or rewrite historical evidence. The read result's currentness is point-in-time; any operation persisting a claim of current evidence must recheck under the invoice row lock.

Task 07a adds private intake-document metadata (generated ID/path, normalized display filename, media type, byte count, SHA-256, UTC timestamps, document state), an editable full-draft JSON/value model with integer revision, and an optional unique confirmed invoice FK. Store files outside webroot on a persistent local volume. File staging and database commit must have explicit compensation for either storage or commit failure; document the recoverable orphan policy. Confirmation locks the document, validates the current draft revision and complete fields, allocates a unique internal invoice ID atomically, and inserts the invoice and confirmation link in one DB transaction. A retry returns the same invoice. Business duplicate policy uses vendor plus supplier invoice number; a matching hash alone warns but does not discard a document. New invoices have no fabricated PO snapshot.

Task 07b adds format-specific PDF/JPEG/PNG validation and extracted page/text provenance under the same document ID; 07c stores separately versioned extraction suggestions with source spans and human edit markers. Suggestions never mutate the draft. The draft `PUT` is a compare-and-swap on `expected_revision`; each successful save increments revision and a stale save returns 409 with the current revision. Extraction completing during editing does not increment draft revision. Persist human-approved values only through the existing 07a confirmation path.

Task 07d adds the smallest independent PO structure: `purchase_orders` (stable internal ID, external reference, supplier identity/reference, currency, VAT/tax terms, integer version), `purchase_order_items` (PO FK, unique positive position, description, positive integer quantity, nonnegative NUMERIC(18,2) unit net), and `invoice_purchase_order_links` (invoice FK, PO FK, status, provenance/source, integer link revision and active snapshot ID) plus `invoice_purchase_order_item_mappings` (invoice line position, PO line position and link revision). Enforce unique invoice and PO positions per active link; each mapping references a real invoice and PO line, even when their positions differ. One active link per invoice. Validate all required lines mapped exactly once, same currency and compatible tax terms before creating a snapshot. Record PO version and mapping provenance on the link; a new snapshot stores PO values in **invoice line order** so Task 04 calculation can reuse its existing rules. Missing/extra lines fail explicitly; no guessed line or delivery receipt.

Existing `invoice_po_snapshots` and `invoice_po_items` remain **unchanged legacy audit rows**. Their current primary key permits one row per invoice, so 07d adds append-only `invoice_po_snapshot_versions` and item rows with stable snapshot IDs for new links/refreshes; it does not update or re-key the legacy row. A new active-snapshot pointer on the link selects the current version; invoices without a new link continue using the legacy snapshot. Add nullable `source_snapshot_id` to `invoice_reconciliations`: existing rows with null resolve to immutable `legacy`, while each new result records the active version's ID in the same transaction. This lets evidence links resolve the exact PO values used by a historical result without changing its payload. Adapt comparison and Task 04 input loading to select the effective snapshot through one repository method, preserving existing DTOs and rounding. **Legacy inputs keep the exact `deterministic-v1` serialization/hash.** A new snapshot uses `deterministic-v2`, adding stable snapshot ID to canonical hash input and extending the result algorithm enum; equal amounts from a different source then create a distinct revision. Currentness compares the stored hash/algorithm to the current canonical version/fingerprint, so legacy evidence is stale after an active new snapshot replaces it. Historical version IDs and legacy ID `legacy` remain resolvable. Backfill the canonical demo as an independent PO/link only through an explicit reversible migration that copies **known** facts, verifies equal totals and leaves legacy rows intact; activation happens only on an explicit linking action. Summary-only invoices remain untouched. A PO edit increments PO version; it does not mutate any issued snapshot or reconciliation payload. A link whose captured PO version lags reports `source_changed` (derived from versions), while its active snapshot remains the comparison source. Task 05 current-PO claims require both a current reconciliation fingerprint and a current link source version. A link refresh is an explicit new revision under the invoice row lock, atomically makes a newly validated snapshot current, and leaves old results readable but stale unless their original hash matches current inputs. Concurrent edits/link attempts use expected versions and return conflict rather than last-write-wins. No destructive migration of existing snapshots.
