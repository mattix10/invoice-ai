# API contract

## Status and source of truth

Health, invoice reads and deterministic reconciliation are implemented. `/openapi.json` and `/docs` are generated by FastAPI and are the implemented contract source of truth. Task 03 generates frontend wire types from that OpenAPI. Do not commit a competing handwritten TypeScript API contract.

## Implemented: infrastructure

| Method / path       | Response                                   | Status                                        |
| ------------------- | ------------------------------------------ | --------------------------------------------- |
| `GET /health`       | `HealthResponse: {"status":"ok"}`          | 200: process serving HTTP, no database access |
| `GET /health/ready` | `HealthResponse: {"status":"ok"}`          | 200: PostgreSQL responds                      |
| `GET /health/ready` | `HealthResponse: {"status":"unavailable"}` | 503: PostgreSQL unavailable                   |

`HealthResponse.status` is `ok | unavailable`; operation IDs are `getHealth` and `getReadiness`. Responses contain no secrets or driver diagnostics. Health checks are not financial or processing status endpoints.

## Implemented: read-only invoice API

Prefix `/api/v1`. Public JSON fields, query parameters and multipart form fields use camelCase; Python attributes and persisted data use snake_case. The field lists below use Python names: for example `gross_amount` is `grossAmount` on the wire. Enum and sort values remain unchanged. Dates are ISO `YYYY-MM-DD`; future event timestamps are RFC 3339 UTC. Monetary values are decimal strings with two fractional digits, never JSON floats; currency is an explicit three-letter ISO code (the demo uses PLN). Quantity is a positive integer for the current demonstration; fractional quantities require a later contract change. This is a breaking change from the previous snake_case wire contract.

### Operations

| Method / path                                  | DTO                 | Status / operation ID                                                                   |
| ---------------------------------------------- | ------------------- | --------------------------------------------------------------------------------------- |
| `GET /api/v1/invoices`                         | `InvoicePage`       | 200 / `listInvoices`; 422 invalid query                                                 |
| `GET /api/v1/invoices/{invoice_id}`            | `InvoiceDetail`     | 200 / `getInvoice`; 404 absent; 422 malformed ID                                        |
| `GET /api/v1/invoices/{invoice_id}/comparison` | `InvoiceComparison` | 200 / `getInvoiceComparison`; 404 absent invoice or absent comparison; 422 malformed ID |

Public IDs follow `INV-YYYY-NNNN` for the existing demo (four or more sequence digits). Enforce bounded length 64 and an anchored ID pattern in OpenAPI. Unknown well-formed IDs return 404. An invoice summary may exist without complete detail; the three dashboard-only records must not acquire fabricated issue dates, line items or purchase orders. Detail can expose nullable fields and an empty item array for summaries; the UI must label unavailable information rather than implying complete extraction. Comparison exists only when a matched PO snapshot is available.

### List request: query parameters

No request body. `page`: integer >=1, default 1. `page_size`: integer 1â€“100, default 20. `status`: optional enum `needs_review | approved | processing`. `q`: optional trimmed string, 1â€“100 characters after trim, case-insensitive literal substring of invoice ID/vendor (escape SQL wildcard characters). `due_from` / `due_to`: optional ISO dates, inclusive, reject inverted range with 422. `sort`: one of `id`, `-id`, `due`, `-due`, `gross_amount`, `-gross_amount`, default `-id`. A minus means descending. Always append ascending ID as a deterministic tie-breaker when sorting another field. No arbitrary SQL column names or expressions from input. Unknown query parameters are rejected with 422. Empty result / out-of-range page returns 200 with empty `items` and accurate `total`.

### Response DTOs

- `InvoiceSummary`: `id: string`, `vendor: string`, `due: date`, `currency: string`, `status: InvoiceStatus`, `gross_amount: Money`.
- `InvoicePage`: `items: InvoiceSummary[]`, `page: integer`, `page_size: integer`, `total: integer` (count after filtering, before pagination).
- `InvoiceDetail`: summary fields plus `issued: date | null`, `purchase_order: string | null`, `vat_rate: decimal-string | null`, `items: InvoiceItem[]`, `totals: InvoiceTotals | null`. Nullability preserves the difference between complete canonical data and dashboard summaries.
- `InvoiceItem`: `position: integer >=1`, `name: string`, `quantity: integer >0`, `unit_net: Money`, `net: Money`.
- `InvoiceTotals`: `net: Money`, `vat: Money`, `gross: Money`. `gross = net + vat`; enforce consistency with item calculations for complete invoices.
- `InvoiceComparison`: `invoice_id: string`, `purchase_order: string`, `delivery_receipt_id: string | null`, `currency: string`, `vat_rate: decimal-string`, `items: ComparisonItem[]`, `invoice_totals: InvoiceTotals`, `po_totals: InvoiceTotals`, `difference: InvoiceTotals`, `difference_percent: decimal-string | null` (null if PO gross is zero).
- `ComparisonItem`: `position`, `name`, `quantity`, `invoice_unit_net`, `po_unit_net`, `invoice_net`, `po_net`; money fields are `Money`, quantity is a positive integer. Quantities match in the current demo; do not invent general receipt-matching behavior.

### Errors

Task 02 defines `ApiError: {"error":{"code":string,"message":string}}` for known application failures. Codes: `invoice_not_found`, `comparison_not_found` (404), `database_unavailable` (503), `internal_error` (500, generic). Request validation retains FastAPI's documented 422 `HTTPValidationError` shape (`detail` array of `loc`, `msg`, `type` and optional fields). Do not leak database errors, bound values or secrets. Document known errors explicitly in OpenAPI. Do not add fictional 401/403 authentication behavior.

## Task 04 reconciliation contract

`POST /api/v1/invoices/{invoice_id}/reconciliation` accepts `{}` (unknown fields rejected) and returns a deterministic completed result with a revision, input snapshot, comparison and per-line net differences. A missing invoice returns 404; missing PO or inconsistent, incomplete or unsupported inputs return 409; malformed requests return 422; database failures return 503. No approval status is changed. The service serializes requests for an invoice using a PostgreSQL row lock, and atomically commits the result. Identical canonical inputs and algorithm version return the existing revision; previously unseen inputs create the next revision; a return to earlier inputs returns their existing revision. Future writers of invoice or PO inputs must acquire the same invoice row lock. The transaction rolls back on any failure; failed attempts do not create a result. Processing transitions from processing to completed within the transaction; only completed results are committed. Results represent deterministic processing only, with no human approval or extraction.

## Planned: read completed reconciliation (05a prerequisite; not yet implemented)

`GET /api/v1/invoices/{invoice_id}/reconciliations/latest` (`getLatestReconciliation`) and `GET /api/v1/invoices/{invoice_id}/reconciliations/{revision}` (`getReconciliationRevision`) return persisted **completed** results only. `latest` means greatest completed revision, including when stale; it never computes a replacement. A positive integer revision and the existing invoice ID pattern are required. Response `ReconciliationRead` has `revision`, `input_hash`, `algorithm_version` (the persisted `ReconciliationResult.algorithm`, currently `deterministic-v1`), `result: ReconciliationResult`, `evidence_refs: EvidenceReference[]`, and `is_current: boolean`. Keep the existing POST response and stored payload compatible. The service verifies that the stored payload's revision/hash/algorithm match its row before exposing it.

`is_current` compares the persisted hash **and algorithm version** with a fingerprint recomputed from **current** invoice/PO inputs using the Task 04 canonical input serialization/calculation. Extract/reuse that hash routine; do not copy its financial rules. Task 07d preserves v1 for legacy snapshots and adds v2 with source snapshot ID for new links; a switched source therefore makes a v1 result non-current even if amounts happen to match. If inputs are missing, invalid or cannot be verified, return the readable historical result with `is_current=false`. A read uses no write transaction and never calls the reconciliation POST or creates a revision. Its currentness is a point-in-time observation: a writer may change inputs after the read. Writers take the existing invoice row lock; a caller that requires current evidence must recheck the fingerprint under that lock immediately before committing any result that claims currentness. A normal conversational response must also revalidate before returning current financial claims and otherwise report stale evidence. Historical revisions stay readable after input changes, including a later reversion to an earlier fingerprint.

Errors use existing `ApiError`: absent invoice `404 invoice_not_found`; no completed result or absent revision `404 reconciliation_not_found`; malformed ID/revision `422 HTTPValidationError`; database unavailable `503 database_unavailable`; corrupt stored result `500 internal_error` with no payload leakage. AI operations requiring current evidence return `409 reconciliation_stale` or `409 reconciliation_unavailable` (missing/invalid inputs); a missing completed result is `409 reconciliation_required`. None triggers reconciliation. Generated OpenAPI becomes authoritative when implemented.

## Planned: evidence references (05a; not yet implemented)

`EvidenceReference` is a server-built DTO: `kind` enum `invoice | invoice_line | po_snapshot | po_line | reconciliation | discrepancy_line`, `invoice_id`, `reconciliation_revision: integer | null`, `line_position: integer | null`, `evidence_id: string`, and `label: string`. `evidence_id` is canonical and stable within its persisted source: `invoice:{id}`, `invoice:{id}:line:{position}`, `invoice:{id}:po-snapshot:{snapshot_id}` (`legacy` for an existing invoice-owned snapshot), `invoice:{id}:po-snapshot:{snapshot_id}:line:{invoice_position}`, `invoice:{id}:reconciliation:{revision}`, or `invoice:{id}:reconciliation:{revision}:line:{position}`. The snapshot ID is encoded in the evidence ID, so later PO edits/relinks cannot redirect historical evidence; 07d records it on new reconciliation rows and treats older null provenance as `legacy`. Validate kind, ID, invoice ownership, snapshot, revision and position against persisted records/results; reject forged or unsupported references with a typed validation error. Historical reconciliation refs may resolve with `is_current=false`; they cannot support a claim about current inputs. A delivery receipt reference string alone is **not** a verified stored document and gets no document evidence ref. The model supplies candidate IDs at most; the server issues validated references and never accepts model-generated URLs.

Angular resolves `invoice` and `invoice_line` to `/invoices/{id}` (line anchor/focus only after validating position), `po_snapshot` and `po_line` to that workspace's comparison section, and `reconciliation` and `discrepancy_line` to `/invoices/{id}/investigation?revision={revision}` (validated focus parameter for a line). These are existing route families; the named anchors/focus behavior is planned for 05c. Unsupported destinations produce an unavailable-link state, never a fabricated PO URL. A future independent PO screen may add a new resolver destination without changing stored evidence IDs.

## Planned: document intake and draft (07a, extended in 07b/07c; not yet implemented)

07a accepts **PDF only**: `POST /api/v1/intake/documents` (multipart, `201` metadata), `GET /api/v1/intake/documents/{document_id}` (metadata, status, draft and revision), `GET /api/v1/intake/documents/{document_id}/file` (private PDF stream), `PUT /api/v1/intake/documents/{document_id}/draft`, and `POST /api/v1/intake/documents/{document_id}/confirm`. The PUT body is `{expected_revision: integer >=0, draft: CompleteEditableDraft}`. `CompleteEditableDraft` has all keys `vendor`, `supplier_invoice_number`, `issued`, `due`, `currency`, `vat_rate`, `items` (`position`, `name`, `quantity`, `unit_net`) and optional source `declared_totals` (`net`, `vat`, `gross`). Each editable scalar may be null/empty while incomplete; items may be empty. Omitted keys are invalid (422), while server validation reports field errors without requiring confirm-ready completeness. Confirmation requires nonempty vendor/supplier number, due date, currency, valid VAT and at least one valid line; issued may be null. Server calculates totals using Task 02 rules; any declared totals must match exactly and client totals never become authoritative. Each successful PUT atomically increments revision by one and returns `{draft, revision, validation}`; even identical PUTs count as updates. Stale revision returns `409 draft_revision_conflict` with `current_revision` (integer) in a documented `DraftConflictError` extension of `ApiError`; the client refetches and presents differences, never silently overwrites. Confirmation takes `{expected_revision}`; requires the current revision and a complete, internally consistent draft; repeated confirmation returns its original invoice ID or `409 already_confirmed`, never a second invoice. `uploaded`, `draft`, `confirmed`, `failed` are document states, separate from invoice status. PDF validation rejects >10 MiB, >20 pages, empty, malformed, encrypted or unsupported files before persistence. File and metadata access remain local-only pending Task 09.

07b extends this **same** intake domain to JPEG/PNG through format-specific validation adapters, metadata and safe previews. Each image is <=10 MiB and <=20 megapixels after decoding; no SVG or URL import. `POST /api/v1/intake/documents/{document_id}/text-extractions` explicitly starts a bounded extraction and returns status/version; `GET /api/v1/intake/documents/{document_id}/text-extractions/latest` returns status and page records `{document_id, page_number, extraction_method, extraction_version, text}` or 404 if none. `GET /api/v1/intake/documents/{document_id}/preview` returns a safe bounded preview, never a storage path. Extraction status is separate from document state and never alters a draft. Unsupported/invalid format is `415 unsupported_document_type` or `422 invalid_document`; size/page/pixel limit is `413 document_limit_exceeded`; encrypted PDF is `422 encrypted_document`; unknown document is `404 document_not_found`; wrong state `409 document_state_conflict`; storage/OCR failure is sanitized `503 storage_unavailable`/`503 extraction_unavailable`. 07c adds `POST /api/v1/intake/documents/{document_id}/suggestions` for deliberate rerun and `GET /api/v1/intake/documents/{document_id}/suggestions/latest` for separately versioned field proposals and source spans (404 if none); neither mutates draft. There is no PATCH draft. Extraction finishing during editing changes suggestions only; accepted suggestions merge into the local full draft and save through revision-protected PUT.

## Planned: independent PO linking (07d; not yet implemented)

07d adds bounded `GET /api/v1/purchase-orders` for real stored candidate summaries and `GET /api/v1/purchase-orders/{po_id}` for detail; `POST /api/v1/purchase-orders` creates a validated fictional PO in local demo mode only. `PUT /api/v1/purchase-orders/{po_id}` updates a PO in local demo mode with `{expected_version, ...complete_po_fields}` and returns the incremented version; active links remain pinned. `PUT /api/v1/invoices/{invoice_id}/purchase-order-link` takes `{purchase_order_id, purchase_order_version, item_mappings:[{invoice_line_position, po_line_position}], expected_link_revision}` and returns link ID/status/revision plus the materialized snapshot identifier. Every required invoice/PO item must be mapped exactly once; differing positions are valid. Unknown invoice/PO returns 404; currency/tax incompatibility, missing/duplicate mapping or existing incompatible link returns `409 po_link_conflict`; malformed values return 422; stale link/PO revision returns `409 po_link_revision_conflict`. Identical retries with the same expected state and mapping return the existing link/snapshot without rewriting it; a changed link requires an explicit new revision. Use the invoice row lock and one transaction. Existing comparison and POST reconciliation routes keep their DTOs and behavior; a missing PO still has no comparison. PO edits use explicit version checks and never alter historical reconciliation payloads. If PO version exceeds the captured version, the link reports `source_changed` until explicit refresh; `ReconciliationRead.is_current` still describes the active snapshot fingerprint only, so AI claiming current **PO source** must additionally require a current link version. See [database.md](database.md) for snapshot compatibility.
