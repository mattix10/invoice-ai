# Task 07a — Working PDF upload, persistent manual draft, confirmation and navigation

**Prerequisites:** actual implemented Tasks 02/03; validate the current invoice/reconciliation code and migrations, don't assume docs mean runtime success. **Goal:** finish a real business journey: a user can upload a previously unseen fictional digital PDF, manually enter invoice data, save/reopen it, confirm it, and see the resulting invoice in PostgreSQL and the existing Workspace. No OCR or live LLM.

## 1. User journeys and UX acceptance

**Existing invoice:** On Overview, `Review next invoice` loads the first real `needs_review` record using documented API sorting and `page_size=1`; routes to `/invoices/:id`. Show appropriate `loading`, `no items`, and `API error` states. No hardcoded `INV-2026-1042` route. Review does **not** mean approve or upload.

**New invoice:** A visible `Upload invoice` action from Overview opens `/invoices/new` (before `:id` route matching). Select PDF → upload → return `document_id` → navigate `/intake/:documentId` → preview **the uploaded file** and show editable fields → **Save draft** genuinely persists partial values → refresh or navigate away and return without losing draft → **Confirm invoice** validates complete input and atomically creates/links a real Invoice row → navigate to `/invoices/{newId}`. This must work even without a PO, with truthful “Comparison unavailable / Awaiting PO” UI. Newly confirmed invoice appears in list/review queue as `needs_review`. Never display the original `INV-2026-1042.pdf` for it. Pending manual confirmation is not an approval/payment decision.

**Design:** preserve existing neutral tokens/sidebar/topbar; dedicated components with separate `.ts`, `.html`, `.scss`, `.spec.ts` files and own folder. Parent pages handle orchestration only; preview/editor/upload widgets are focused components. Reuse existing API mapping and components when suitable, without turning old invoice details into a monolithic page. Accessible real buttons, field labels, validation messages and keyboard interactions. Upload, save and confirm must not be inert.

## 2. Backend API — finalize schemas in generated OpenAPI

- `POST /api/v1/intake/documents` multipart PDF (<=10 MiB streaming), respond **201** `{document_id,status:'uploaded',original_name,size_bytes,created_at}`; do not parse financial fields.
- `GET /api/v1/intake/documents/{document_id}` retrieve intake metadata + status and draft revision (404 unknown).
- `GET /api/v1/intake/documents/{document_id}/file` stream private PDF with safe response type and content-disposition; never expose filesystem/storage path.
- `PUT /api/v1/intake/documents/{document_id}/draft` accepts `{expected_revision, draft}` where **all editable keys** (`vendor`, `supplier_invoice_number`, `issued`, `due`, `currency`, `vat_rate`, `items` with `position/name/quantity/unit_net`, optional `declared_totals`) are represented but values may be null/empty while incomplete. It atomically compares the integer revision, validates the full representation, increments revision on every successful save and returns `{draft, revision, validation}`. Stale revision gives `409 draft_revision_conflict` with `current_revision`; the client refetches and offers conflict resolution, never overwrites silently. Save does not create an Invoice row. 07c uses this same PUT, not PATCH.
- `POST /api/v1/intake/documents/{document_id}/confirm` takes `{expected_revision}`, requires complete validated draft and idempotency/revision protection; returns `{invoice_id,status:'confirmed'}`. A complete draft has vendor/supplier number, due date, currency, VAT and at least one valid item; issued may be null. Server calculates totals and rejects contradictory optional declared totals. Repeat confirmation returns prior result or documented conflict, never creates duplicate invoice. Unknown docs 404; wrong status/conflict 409; missing/incomplete fields 422; server errors sanitized. Follow the current project error contract.

Use `InvoiceService` and the existing calculation domain for invoice creation; no duplicate independent invoice-model schema or calculator. Add `supplier_invoice_number` only when needed with a reviewed migration, distinguish supplier number from internal `INV-YYYY-NNNN`. Exact money string DTOs and `Decimal`; no client-side authoritative calculation. Persist files privately outside static hosting with generated safe server filenames, metadata, SHA-256, timestamps and draft data/revision. Use Alembic for metadata/relations. The local stored file persists through Docker restart (volume if needed); fail cleanly on filesystem errors; cleanup orphan temporary files; never commit documents to repo.

Document states are `uploaded → draft → confirmed`; `failed` records rejected processing without implying an invoice. `uploaded` has no invoice; `draft` may be incomplete; `confirmed` points to exactly one invoice and cannot be edited. Wrong state is `409 document_state_conflict`. Unknown document is `404 document_not_found`; wrong format `415 unsupported_document_type`; empty/malformed document `422 invalid_document`; encrypted document `422 encrypted_document`; limit exceeded `413 document_limit_exceeded`; storage failure `503 storage_unavailable` with no path leakage. Confirm with stale revision returns `409 draft_revision_conflict`, incomplete/invalid draft 422, and repeated confirm returns original invoice ID or documented `409 already_confirmed` idempotently. Match `ApiError` and FastAPI validation shapes in the planned API contract. The UI must distinguish upload, save, fetch, file and confirm failures.

Generate **unique concurrent-safe internal IDs** with DB sequence/unique constraint or another documented atomic allocation. Do not use `SELECT max(id)+1` without concurrency protection. Preserve confirmed records on retries and never overwrite previous records. Duplicate checks: SHA and vendor + supplier invoice number; safe conflict/warning and explicit resolution, not silent dedup. Store original display filenames only as normalized data, never as path. Be careful not to create fake complete PO snapshots.

## 3. Security and scope

Only PDF in 07a. Enforce **10 MiB maximum while streaming** and **20 pages maximum** before persistence; reject empty, malformed, encrypted/password-protected PDFs, unsupported extensions/MIME and false signatures. Verify `%PDF` signature **and** bounded PDF structure/page parsing; a matching magic prefix alone is insufficient. Bound parser time, memory and object expansion, using process isolation where a hard in-process limit is unavailable; do not render pages in 07a. Normalize display filename but generate the storage path server-side outside public directories, never follow user path components, clean up partial files and sanitize errors. Limit the environment to loopback/local development and document explicit non-production use until Task 09. Do not trust `X-Forwarded-For` as an authentication mechanism. This is not a malware scanner. No OCR, image upload, email, cloud storage or public exposure.

**Dependency request before implementation:** add `python-multipart` (Apache-2.0; Python >=3.11) for FastAPI streaming multipart parsing, and `pypdf` (BSD-3-Clause; Python >=3.9) for PDF page count, structure and encryption validation. Existing backend dependencies provide neither capability. Both are pure Python and suitable for Python 3.13 on Windows and Docker; no system binary is required in 07a. Pin reviewed versions in `pyproject.toml`/`uv.lock` only after listing exact additions for user approval. Review parser resource limits and untrusted-file advisories; CI needs locked installation, malformed/encrypted/page-limit fixtures and a container smoke. [python-multipart metadata](https://pypi.org/project/python-multipart/); [pypdf metadata](https://pypi.org/project/pypdf/). No dependency is installed by this specification.
