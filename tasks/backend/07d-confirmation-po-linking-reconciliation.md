# Task 07d — Link actual PO and reconcile an already confirmed uploaded invoice

**Prerequisites:** 07a persistent manually confirmed invoices; 07b/07c optional for user-selected field suggestions; Task 04 deterministic reconciliation. **Do not recreate 07a's draft form or confirmation flow.**

## Business use case

User sees the confirmed imported invoice in Workspace. If no actual corresponding purchase order (PO) exists, comparison shows **Not available / Awaiting PO**; never display the golden fixture's PO. User can link a real independent stored PO or create a **minimal, validated fictional PO** in local demo mode. Then explicitly run deterministic reconciliation and see recorded evidence and real difference. AI may explain the result later; it does not authorize purchase decisions.

## Deliverables

- Add `PurchaseOrder` (stable ID, external reference, supplier identity/reference, currency, VAT/tax terms, integer version) and `PurchaseOrderItem` (unique positive position, description, positive integer quantity, nonnegative Decimal unit net). Add `InvoicePurchaseOrderLink` (invoice/PO FKs, status/provenance, integer link revision, active snapshot ID) and explicit item mappings `(invoice_line_position, po_line_position)` with one-to-one uniqueness. Different position numbers are valid; every required line must map exactly once. Do not build an ERP or broad procurement subsystem.
- `GET /api/v1/purchase-orders` lists bounded genuine candidates; `GET /api/v1/purchase-orders/{po_id}` gets detail; local-demo-only `POST /api/v1/purchase-orders` creates validated fictional PO; local-demo-only `PUT /api/v1/purchase-orders/{po_id}` takes `expected_version` and complete PO fields, returning an incremented version. `PUT /api/v1/invoices/{invoice_id}/purchase-order-link` accepts PO ID/version, full item mapping and `expected_link_revision`, returning link status/revision and immutable snapshot ID. Define exact DTOs, operation IDs and errors in generated OpenAPI. Existing GET comparison and POST reconciliation remain compatible.
- Keep existing `InvoicePoSnapshot`/item rows unchanged as legacy audit data. Add append-only versioned snapshot rows/items for new links; store mapped PO lines in invoice-line order, using the existing calculator without guessed lines. A repository method selects active new snapshot or unchanged legacy snapshot for comparison/reconciliation. Add nullable `source_snapshot_id` on reconciliation rows: old null rows mean `legacy`, new rows record the snapshot version used. Keep **exact** v1 hash/algorithm for legacy inputs; use `deterministic-v2` for new snapshots with snapshot ID in canonical hash input, so equal amounts from different PO sources do not collapse into one revision. Extend the response algorithm enum compatibly and keep old payloads readable. Do not destructively backfill. The canonical demo PO may be copied into an independent record by a reversible, verified migration, but legacy snapshot activation stays unchanged until an explicit link action; existing reconciliation payload/hash remains valid. See `docs/architecture/database.md`.
- Ensure `InvoiceRepository` and deterministic calculator remain single sources of truth for amounts; typed Pydantic schemas and existing decimal-string OpenAPI contract, no LLM calculations.
- Enforce invoice/PO currency compatibility, positive quantities and prices, item mappings, revision/idempotency, existing PostgreSQL transaction/row locking semantics. Record provenance and source type (`existing` / human-entered demo); no silently guessed PO, vendor history or receipt.
- A PO edit requires its expected PO version and increments it; old snapshots/results remain immutable. The current link stays pinned to the captured PO version until an explicit refresh and reports derived `source_changed` when the PO advances. `ReconciliationRead.is_current` compares the active snapshot fingerprint, so a Copilot/MCP claim about the **latest PO source** must additionally require a current link version; do not call an old snapshot a current PO. Refresh/relink locks the invoice row, checks `expected_link_revision` and PO version, validates all mappings and totals, writes a new immutable snapshot and atomically switches the active pointer. Identical retry with the same link/mapping/version returns the prior result; competing changes return 409. Concurrent invoice/reconciliation writers take the same invoice lock. Old revisions remain readable but may have `is_current=false`; no automatic reconciliation or silent historical rewrite.
- Reuse the existing Invoice Workspace comparison and reconciliation views. Preserve one AppShell and focused Angular component folders. Offer `Link PO`, `Run reconciliation` and `Investigate` when prerequisites exist; surface missing PO and missing receipt honestly.

## Acceptance and tests

- For the canonical fixture the existing 500.00 net/115.00 VAT/615.00 gross discrepancy remains exact. For a *new* uploaded fictional invoice, link different PO amounts and see a new correct variance; zero variance is also possible.
- Missing/invalid PO, mismatched currency, duplicate link, bad item positions, empty PO, concurrent/retried reconciliation and rollback produce documented errors without partial writes.
- Unknown invoice/PO is 404; malformed request is 422; currency/tax mismatch, missing/duplicate mapping or incompatible existing link is `409 po_link_conflict`; stale link/PO version is `409 po_link_revision_conflict`; database failure 503. Missing PO keeps comparison absent (existing 404) and UI `Awaiting PO`. Unit tests cover reordered positions, amount/rounding/currency validation, missing mappings, idempotency and error DTOs; real PostgreSQL tests cover FKs/uniqueness, concurrent link/reconciliation, rollback, PO update after reconciliation, historical snapshot/result readability, unchanged canonical hash and migration round trip.
- Audit records point to real invoice/PO/reconciliation versions. Idempotent repeats do not duplicate reconciliation rows. No payment/approve workflow.
- Backend pytest/real PostgreSQL: FK and amount invariants, concurrency, rollback and idempotency, migration round trip; frontend Vitest: PO selector/edit state, missing/comparison errors, safe retry, results route/UI. Existing CI green. No real cloud/model call or public endpoints.
