# PR demo video

Invoke as `$pr-demo-video 42` for PR 42, or `$pr-demo-video` for the PR associated with the current branch. Work from the repository root. Do not create, merge, or close PRs, or upload during initial skill setup.

## Prerequisites

- Node and npm; install the official CLI with `npm install -g @playwright/cli@latest`, then `playwright-cli install --skills=agents`. Check `playwright-cli --version` and its video command help for `--cursor` and `--fps`; upgrade if missing. Consult the installed Playwright skill's video-recording reference or [official documentation](https://github.com/microsoft/playwright-cli/blob/main/skills/playwright-cli/references/video-recording.md) for current syntax.
- GitHub CLI 2.99.0 or newer: check `gh --version`, `gh auth status`, and `gh pr edit --help` for `--attach`. Authentication and repository permission are required to update the PR.
- A running local InvoiceAI instance and safe synthetic data. FFprobe or another reliable media inspector is needed to verify encoding, duration, dimensions and frame rate; FFmpeg is optional for compression. Never use production credentials or real customer data, reset a database, or modify production code to make a demo pass.

## Workflow

1. Resolve the PR using the supplied number or `gh pr view --json number,url,body,headRefOid`; obtain the diff with `gh pr diff <number>` and relevant acceptance criteria from the PR or linked task. Check that the running checkout represents the PR changes. Read only this skill, the relevant diff and criteria, and targeted code or existing scenario scripts when needed. Do not launch additional agents or repeatedly explore the app.
2. Select one short, meaningful path that actually exercises the implemented change. For backend changes, consider the local Swagger/OpenAPI UI or another browser-visible API operation, showing the request and actual response; a frontend feature is not required. Use safe synthetic data, existing fixtures, and stable accessible selectors. Respect task restrictions on live inference and external calls; mocked responses must be clearly identified and must not be presented as live behavior. Confirm any claimed persistence against actual persisted state. Do not suggest fixture content proves OCR, AI, or backend behavior that is not implemented. Skip only when no truthful, meaningful browser-recordable demonstration is available.
3. Start the app using its existing local setup without destructive data operations. Record actual Playwright interactions and assertions, preferably in a single `playwright-cli run-code --filename <script>` execution. Keep output concise and avoid repeated DOM snapshots. Save a small reusable scenario only when useful; avoid a generic framework. Use `.pr-demo-video/` for temporary scripts, body files and recordings; do not commit recordings.
4. Use Chromium, a 1280x720 viewport and a 60 FPS target. The official `playwright-cli video-start .pr-demo-video/demo.webm --cursor --fps=60` provides a visible animated cursor. For a scripted recording use `page.screencast.start({ path, size: { width: 1280, height: 720 }, fps: 60 })` and `page.screencast.showActions({ cursor: 'pointer', duration: 800, style: { title: 'display: none' } })`; stop the screencast in cleanup. Use locator actions that the built-in cursor can animate; never teleport or fake interactions. Aim for curved 600–900 ms transitions, natural typing, short pauses after changes, a visible outcome, 20–45 seconds, and no unnecessary scrolling, music or camera effects.
5. If any assertion fails, do not attach. Inspect the resulting video with a media inspector: file exists, valid duration, 16:9 dimensions, 60 FPS target, supported WebM/VP8 or VP9 or MP4 encoding, and below 10 MB. Watch playback to check the cursor stays visible, moves smoothly and the flow is legible; metadata alone cannot prove this. If playback cannot be checked, report that limitation rather than claim quality. Compress or convert with FFmpeg only if necessary, preserving smooth playback, and recheck the output. Retry recording only when needed.
6. Fetch the latest PR body immediately before editing. Preserve the title and all unrelated body content. Replace the existing region bounded by `<!-- pr-demo-video:start -->` and `<!-- pr-demo-video:end -->`, or append one if absent. If markers are malformed or ambiguous, stop rather than overwrite content. Inside the markers add `## Feature Demo`, a short flow description, assertion/verification result, relevant limitations, and a Markdown reference to the local video, e.g. `![Feature demo](./demo.webm)` when the body file and video share a directory. Write the complete updated body to a UTF-8 file in `.pr-demo-video/` and run `gh pr edit <number> --body-file <body-file> --attach <video-file>`; GitHub CLI uploads and rewrites the referenced local path to the asset URL. Do not guess URLs. If the body has changed since the fetch, refresh and reconstruct it before editing. Inspect the command result even on failure: partial uploads can still update the PR.
7. Fetch the PR body again and verify exactly one marked demo section contains the new uploaded video reference and unrelated text remains intact. Report success only after this check. If authentication, permissions, upload, or verification fails, keep the local video and report the exact blocker. On reruns repeat this replacement workflow rather than appending duplicate sections.

Troubleshooting: check the CLI versions and help, local app availability, safe test data, browser installation and media inspection tools. If an interaction or assertion fails, diagnose the actual application state; do not present a failed recording as success. If no meaningful browser-recordable scenario exists, explain why recording was skipped.
