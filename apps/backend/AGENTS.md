## Boundaries

- Modular monolith, feature-first under `src/invoiceflow/modules/`. Do not create empty module scaffolds.
- Routers own HTTP validation, response contracts and delegation. Services own use cases and transactions without HTTP dependencies. Repositories own concrete database operations without business decisions. Add layers when a capability needs them; health checks do not need a business service or generic repository.
- Inject dependencies explicitly. Application resources belong to the app lifespan, sessions to requests. No shared mutable session or import-time database connections. Use synchronous routes with the synchronous psycopg/SQLAlchemy stack.
- Pydantic v2 schemas are distinct from SQLAlchemy models. OpenAPI generated by the application is the implemented API source of truth; architecture documents specify planned contracts until their task is implemented.
- Money uses Decimal / NUMERIC, explicit currency and independently tested rounding. Never use float for money. Dates use ISO date values; event timestamps are timezone-aware UTC.
- No generic helpers/utils, speculative facades, base repositories, CQRS, background brokers or authentication stubs. No OCR, AI, approvals, payment or deployment in Task 01.
- No startup `create_all` or automatic migrations. Review explicit Alembic revisions; check metadata consistency against PostgreSQL. The Task 01 baseline has no domain tables by design.
- Keep secrets in environment variables. `.env.example` contains fictional local-only credentials. Local unauthenticated endpoints bind to loopback; this is not a production security boundary.

## Required verification

From `apps/backend`: `uv sync --locked`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run pytest tests/unit`, `uv run pytest tests/integration`, `uv run alembic upgrade head`, `uv run alembic check`. Integration tests require a real PostgreSQL database whose name ends in `_test`; do not skip them or fall back to SQLite. See local-development documentation for isolated setup and commands.

Verify Docker build/startup, health/readiness, migration round trip on an isolated test schema, frontend quality gates and workflow configuration. Report actual counts and blockers. Update `docs/PROGRESS.md`, inspect the final diff, and stop after the assigned task.
